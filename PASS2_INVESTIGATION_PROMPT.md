I'm investigating a performance issue in this Blender add-on (`yt-volumes`). Context on what's already been done:

**Already fixed and committed** (see commit `7ab1e9a`, "Fix pass1/pass2 compositor node ping-pong causing full rebuild every frame"): a severe bug where pass1's and pass2's compositor graphs shared one node-cleanup sweep (`_clear_managed_nodes` in `compositor_build.py`), so each pass's "is my node already there?" check kept tripping over the other pass having just deleted everything — both compositor graphs were being torn down and rebuilt from scratch, twice, every single frame. That's fixed and verified: pass1's own render step is reliably back to ~0.7s/frame (from ~3.9-4s).

**Unresolved:** pass2 (the "cheap," Image-node-only compositor render, `bpy.ops.render.render(write_still=True)` in `operators.render_current_frame`, in `src/yt_volumes/operators.py`) still takes ~4s/frame in a full real end-to-end run, when it should be ~0.9s based on isolated testing. Specifically:

- Running `scripts/yt_idv_exploration/blender_scene/render_headless.py` (real `.blend` file, real yt_idv, real Cycles/OptiX) shows pass2 consistently at ~4.0-4.1s per frame in the verbose log output (`[VolumeOverride] ... DONE pass2 render ...`).
- But hand-assembling the exact same sequence of calls in an isolated script (calling `compositor_build.build_pass1_capture_graph`, `bpy.ops.render.render`, `operators.write_render_result`, `compositor_build.build_or_update_graph`, `bpy.ops.render.render(write_still=True)` directly, with a completely real preamble replicated by hand — `properties.flagged_objects`, `scene_sync.sync_scene_state`, `operators._sweep_stale_frame_dirs`, `operators.build_camera_params`/`build_frame_params`/`build_volume_params`, `operators._apply_opacity`) reproduces the slow pass2 too — UNTIL `_sweep_stale_frame_dirs` is called only once instead of per-frame, which fixed it in that isolated harness.
- BUT: applying that exact fix to the real code (moved the sweep into `render_session.__enter__`, guarded the per-frame call in `render_current_frame` with `if _active_render_session is None:`) did NOT fix the real `render_headless.py` run — pass2 there is still ~4s. I directly verified the sweep is correctly only being called once (not per-frame) even through the real `bpy.ops.render.volume_override` operator path, and that module identity (`yt_volumes.operators`) is consistent — so it's not a stale-module-reference issue.

So there's something about the *real* end-to-end pipeline that reproduces this ~3s pass2 regression which isn't captured by my isolated reproduction, even though the isolated reproduction pointed at (and "fixed") the sweep call. Already ruled out as sole causes: `compositor_device` CPU vs GPU, frame-stepping alone, `sync_scene_state` alone, verbose logging, module-reload/identity mismatch, yt_idv/EGL interleaving.
